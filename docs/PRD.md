## 1. 产品定位

一句话：**告诉它你想吃什么味道、手头有什么食材，它给你几道可选的菜，并带你一步步做出来。**

与现有菜谱网站的差异：

| | 传统菜谱站 | 本产品 |
|---|---|---|
| 入口 | 搜菜名 | 拍一下/选食材 + 选风味 |
| 内容 | 固定菜谱 | 按用户的食材、厨具、忌口现做一份 |
| 范围 | 以单一菜系为主 | 跨菜系，同一食材给出不同国家的做法 |
| 越用越准 | 否 | 是（可选记录个性化数据） |

### 1.1 三条设计原则【已定】

后续所有功能取舍都以这三条为准。

**原则一：产品解决的是“做决定”，不是“找菜谱”。**
用户的难处在从“今天吃什么”到“开火”之间的犹豫。因此每次只给 3–5 道、刻意跨菜系、标明还要买什么，让人能马上选定；不做大而全的菜谱检索。

**原则二：知识库用来“约束和结构化”，不用来“教模型做菜”。**
模型本身已懂各国菜。知识库承担三件事：驱动选择界面、约束生成结果使其符合菜系风格、统一味型/难度/技法的叫法。它存菜系的风味特征、核心调料、代表技法，不存完整菜谱。

**原则三：为海外中文厨房而设计。**
买不到的食材给替代方案并说明风味差别；食材附英文名；公制与美制单位可切换；按烤箱、空气炸锅、电炉的实际条件给做法。

## 2. 目标用户【已定】

**第一版：海外中文用户中“会做饭但缺灵感”的人。**

- 基本功有，不需要教“怎么切葱”，需要的是**新想法**和**清晰的关键点**（火候、顺序、容易失败的地方）。
- 海外生活带来的具体约束：
  - 部分中餐食材和调料买不到或很贵；
  - 当地超市的常见食材（牛油果、三文鱼、奶酪、整鸡、各种香草）不知道怎么做得合口味；
  - 厨房普遍有烤箱，不少人有空气炸锅，但多数是电炉/电磁炉，火力不如明火；
  - 计量单位混用（克/毫升 与 cup/oz/°F）。
- 语言：界面与内容为简体中文；食材名附英文。

暂不针对：纯新手、专业厨师、中国大陆用户（涉及网络可达性与合规，后续版本再评估）。

## 3. 核心使用流程

```
食材（拍照或输入）→ 风味（可加场景）→ 3–5 道推荐 → 选一道 → 教程 → 烹饪模式 → 评价
   ↑                                                                        │
   └──────────────── 评价与历史用于改进下一次推荐 ──────────────────────────┘
```

1. **食材**（先问食材，理由见 4.2）
   - 拍照：拍冰箱或台面，识别出食材清单，用户确认后使用（见 4.1）。
   - 输入：有联想，也可从“常用食材”点选。
   - 在清单中勾选“今天想用的主料”（1–5 种），其余视为“手头还有”。
2. **风味与场景**：味型标签多选（最多 3 个），可选一个场景标签，可选指定菜系；什么都不选即“随便，给我惊喜”。
3. **推荐结果**：3–5 道菜，覆盖不同菜系/做法。每道显示：菜名、菜系、一句话风味描述、预计时间、难度、**还需要补充的食材**。支持“换一批”。
4. **教程**：选定后生成完整做法（见 4.3）。
5. **烹饪模式**：一屏一步（见 4.4）。
6. **评价**：做完后一键反馈（好吃 / 一般 / 不会再做），可选填一句原因。

目标：已登录用户从打开到看到推荐，30 秒内完成。

**风味与场景的交互结论【已定，依据见附录 A】**

- **先食材，后风味。** 调研显示，决定晚饭做什么的首要因素是时间和手头有什么，而不是口味；有了拍照识别后，食材也是最省力的起点。
- **风味是本产品的差异点，保留为主要选择**，但不作为唯一维度。
- **增加“场景”标签，不增加“心情”入口。** 场景对应的是时间、费事程度、场合这些真实约束；“按心情选菜”目前只见于概念性项目，没有找到被验证过的做法，且与风味重叠。
- **场景不是独立入口**，而是风味下方的一行可选标签，避免把一步选择变成两步。
- 每个场景标签在系统内翻译成明确的约束（见 5.2），而不是把“下饭”两个字直接丢给模型。

### 4.3 教程内容

每份教程固定包含以下结构：

- **概览**：菜名（中/英/原文名）、菜系、风味描述、总时间、难度、份量。
- **食材清单**：分“主料 / 辅料 / 调料”；用量随份量缩放；公制与美制单位可切换；每项附英文名。
- **替代方案**：对海外不易买到的食材给出替代，并说明风味上的差别。
- **步骤**：每步一个动作，写明火力、时间、**判断标准**（“炒到边缘微焦”而不是只写“炒 3 分钟”）。
- **关键点**：这道菜最容易失败的 1–3 处。
- **背景**（可折叠）：这道菜/这种技法在该菜系中的位置。

| 编号 | 需求 | 优先级 |
|---|---|---|
| F16 | 按上述结构生成教程，流式显示 | P0 |
| F17 | 份量缩放、单位切换 | P0 |
| F18 | 食材替代方案 | P0 |
| F19 | 收藏教程；收藏的内容固定保存，不会再次生成时变样 | P0 |
| F20 | 针对当前教程追问（“没有料酒怎么办”“可以用空气炸锅吗”） | P1 |
| F21 | 菜品图片（见下） | P0 |

**菜品图片【已定：纳入第一版】**

- **每道菜一张 AI 生成的成品示意图**，**推荐卡片和教程顶部都显示**，标注“AI 生成示意图，成品可能不同”。卡片与教程用同一张图，选中一道菜后不再另外生成。
- **共享图片库**【已定】：凡是生成过的图片都存入图片库，任何用户再遇到同一道菜直接取用，不重复生成。
  - 按“标准菜名 + 菜系”匹配。推荐结果里每道菜都带标准中文名和英文名，系统据此对到菜品词典；词典里没有的新菜自动加入。
  - **只复用同一道菜的图**。相似但不同的菜（如“鱼香茄子”与“红烧茄子”）不借用图片，以免图文不符误导用户。
  - 推荐时把图片库里与用户食材、风味相符的已有菜品一并交给模型参考，在同样合适的情况下优先推荐已有图片的菜。这样能提高复用率，也让被验证过的好菜更常出现。不设硬性比例，以免推荐变得单调；上线后观察复用率再调。
- **预先生成一批**：上线前为约 1,000 道常见菜生成图片（14 个菜系的代表菜及常见家常菜），一次性花费约 $40，让常见菜从第一天起就有图。
- **不阻塞文字**：推荐卡片和教程的文字先显示；图片库里有的图立即显示，没有的在后台并行生成，期间显示占位图（按菜系配色），生成后自动补上，通常需要十几秒到一分钟。生成失败则保持占位图，不影响使用。

## 5. 知识库

### 5.1 定位【已定】

见原则二。知识库承担三件事：

1. **驱动界面**：风味标签、场景标签、菜系列表、食材联想都从知识库来。
2. **约束生成**：把所选菜系的风味特征、核心调料、代表技法作为上下文交给模型。
3. **保证一致**：统一味型、难度、技法的叫法，使推荐可比较、可筛选、可统计。

菜谱由模型实时生成，知识库不存完整菜谱（代表菜只存名称与要点，作为风格锚点）。

### 5.2 内容结构

**菜系条目**（每个菜系一份）：

| 字段 | 说明 | 示例（川菜） |
|---|---|---|
| 概述 | 2–3 句风格总结 | 善用麻辣，味型多变，“一菜一格，百菜百味” |
| 典型味型 | 该菜系的代表性风味组合 | 麻辣、鱼香、宫保、怪味、蒜泥、酸辣 |
| 核心调料 | 决定风味的关键调料 | 郫县豆瓣、花椒、干辣椒、泡椒 |
| 代表技法 | 常用烹饪方法及要点 | 小炒（急火短炒，一锅成菜）、干煸、水煮 |
| 常用食材 | 高频主料 | 猪肉、牛肉、豆腐、茄子 |
| 代表菜 | 10–20 道，仅名称与一句要点 | 麻婆豆腐、回锅肉、鱼香茄子 |
| 海外可得性 | 关键食材/调料的替代建议 | 郫县豆瓣 → 亚洲超市可得；无则用韩式辣酱 + 味噌近似 |

**味型标签**（面向用户，跨菜系）【已定】：

- 首屏显示（8 个）：酸辣、麻辣、咸鲜、清淡、蒜香、甜口、浓郁、香料浓郁（咖喱类）
- “更多”中：酸、甜辣、烟熏/炙烤、香草清新、奶香、发酵鲜味（酱、味噌、鱼露）

每个标签在知识库中映射到“哪些菜系擅长这种味道”，用于让推荐跨菜系。

**场景标签**【已定】——每个标签对应一组明确约束：

| 场景 | 系统内的约束 |
|---|---|
| 快手 | 总时间 20 分钟内，步骤不超过 6 步 |

## 6. AI 能力设计

### 6.1 四类调用与模型选择【已定，依据见附录 B】

| 环节 | 输入 | 输出 | 模型 | 要求 |
|---|---|---|---|---|
| 拍照识别 | 1–3 张照片 | 食材清单（含把握程度） | gpt-6.1-terra | 5 秒内 |
| 推荐 | 食材、风味、场景、个性化摘要、相关知识库条目 | 3–5 道候选菜 | gpt-6.1-terra | 5 秒内出首条 |
| 教程 | 选定的菜、用户条件、该菜系知识库条目 | 完整教程 | gpt-6.1-sol | 流式输出，质量优先 |
| 追问 | 当前教程 + 用户问题 | 简短回答 | gpt-6.1-terra | 3 秒内 |
| 菜品图片 | 菜名、菜系、成品描述 | 一张成品示意图 | OpenAI 当前推荐的图片模型，中等质量 | 仅图片库没有时生成；后台并行，不阻塞文字 |

- 图片模型的具体型号以 OpenAI 模型页为准（官方文档中的命名前后不一致，接入时核对）。
- 选型理由：教程是用户真正照着做的内容，用质量更高的型号；其余环节任务简单、对速度更敏感，用便宜一档的型号。
- 最高档的 gpt-6-astra 单价是 gpt-6.1-sol 的 5 倍，第一版不作为默认；在评测中与 gpt-6.1-sol 对比，若教程质量差距明显再考虑。
- 每个环节的模型都是配置项，可随时更换，不写死在代码里。
- 输出均为固定结构，界面按结构渲染。
- API 密钥只在服务端。

### 6.2 质量与安全【已定】

- **硬性约束**：过敏原与忌口在提示词中声明，并在输出后做一次程序检查（食材清单与过敏原比对），命中则重新生成。
- **食品安全**：禽肉、猪肉、海鲜等的熟度要求写入系统规则；涉及生食、发酵、低温慢煮时给出提示。
- **非烹饪输入**：与做菜无关或不可食用的输入礼貌拒绝；与食物无关的照片提示重拍。
- **免责说明**：教程由 AI 生成，过敏与饮食禁忌请自行确认。
- **评测**：建立一组固定测试用例（30 组“食材 + 风味 + 场景”组合，另加 20 张食材照片），每次改提示词或换模型后跑一遍，人工抽检。

## 附录 A：风味与场景调研

**问题**：风味怎么选？是否需要“场景”或“心情”入口？

**查到的情况**

- 决定做什么菜的主要因素是时间和手头的食材。美国食品营销协会 2015 年的调查中，工作日做饭最看重的是省时省事（36%）、花费（35%）、健康（29%）；另有调查称约五分之一的人由冰箱和橱柜里现有的东西决定晚饭。
- 英国一项调查中，42% 的人靠盯着冰箱找晚饭灵感，48% 的人翻橱柜；三成的人定好了菜才发现缺食材。
- 澳大利亚一项调查中，62% 的人觉得决定晚饭做什么有压力，首要压力来源是照顾多人的不同口味与需求（35%）。
- 菜谱应用的设计指南普遍把时间、份量、忌口、食材、厨具、难度、场合列为选菜要展示的信息；常见筛选维度是餐别、菜系、时间、忌口。中文菜谱应用常按食材、类别、口味、菜系分类。
- “按心情选菜”只在概念性或个人项目中出现，没有找到被验证有效的实例。

**结论**（已写入 4.2 与 5.2）

先问食材，再选风味；增加一行可选的场景标签并映射为明确约束；不做心情入口。

**这部分调研的局限**

- 上述调查多为品牌委托，年份偏旧（2015–2017），问法各不相同，数字只能说明方向，不能直接比较。
- 没有找到“用户按口味选菜的比例”这类直接数据。风味标签的具体清单是设计判断，不是调研结论，需上线后用点击数据校正。
- 下厨房、美食天下等中文菜谱站的分类页未能读取（有验证码或访问限制），对它们分类体系的描述来自应用商店介绍和第三方文章。
